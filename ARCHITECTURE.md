# Архитектура

## Сейчас

```
Сайт (Claude Design canvas, claude.ai)
   │  кнопки «Записаться» ведут на отдельный домен
   ▼
Booking UI (Next.js App Router, этот проект)
   │  fetch к своим же API-роутам
   ▼
Backend API (Next.js Route Handlers, src/app/api/**)
   │  Prisma
   ▼
PostgreSQL (bookings, services, blocked_slots, settings)
   │
   ▼
Telegram Bot API (webhook: src/app/api/telegram/webhook/route.ts)
   ├── админ-чат — уведомления о заявках, команды /today /week /free /block …
   └── чат клиента — статус заявки (после /start по диплинку)
```

Два физически разных проекта: канвас (визуальный прототип на claude.ai, без
бэкенда) и это Next.js-приложение (настоящий сервер). Их соединяет только
ссылка — кнопка «Записаться» на канвасе указывает на URL этого приложения.

## Почему так, а не всё в канвасе

Канвас — это статичные `.dc.html`-артборды, которые рендерятся в
изолированном iframe без доступа в сеть (это осознанное ограничение
инструмента ради безопасности, а не то, что можно включить/выключить).
Он физически не может держать секреты, стучаться в БД или вызывать
Telegram API. Поэтому реальная логика бронирования не может жить внутри
канваса ни при каком раскладе — только рядом, отдельным сервисом.

## Почему домен, а не встраивание в iframe

По той же причине (no-egress sandboxed iframe) канвас не может встроить
живое Next.js-приложение как iframe с сохранением интерактивности —
максимум, что доступно изнутри канваса, это ссылка `<a href>`. Поэтому
booking открывается как переход на отдельный URL (домен/поддомен), а не
как модалка поверх текущей страницы.

## Куда двигаться дальше — перенос всего сайта в Next.js

Если в будущем понадобится объединить маркетинговый сайт и бронирование
под одним доменом и одним деплоем, естественный путь:

1. Перенести разметку и стили из `Main.dc.html` (канвас) в
   `src/app/page.tsx` этого же Next.js-проекта как статические React-
   компоненты — один в один, без реализации заново: тот же CSS
   (переменные из `globals.css` этого проекта уже используют ту же
   палитру — `#0b0a09`/`#d98a3d`/Jost+Manrope, — так что стили не
   потребуется придумывать заново).
2. Разбить секции сайта (`Hero`, `Uslugi`, `Studio`, `Raboty`,
   `Booking`, `Kontakty`) на отдельные React-компоненты в
   `src/components/site/*`, по аналогии с тем, как уже разбит
   `src/components/booking/*`.
3. Кнопка «Записаться» тогда становится обычным `<Link href="/booking">`
   внутри одного и того же приложения — переход мгновенный, без ухода на
   другой домен.
4. Backend (API-роуты, Prisma, бот) трогать не нужно вообще — он уже
   живёт в этом же проекте и ничего не знает о том, что рядом появился
   ещё и маркетинговый сайт.
5. Дизайн-канвас на claude.ai после переноса можно оставить как архив
   истории дизайна (он не мешает и не требует поддержки) либо просто
   перестать обновлять.

То есть перенос — это на 90% копирование HTML/CSS в JSX и объявление
общих переменных темы, а не переписывание бэкенда: он уже спроектирован
как отдельный, самодостаточный слой именно с расчётом на этот сценарий.

## Данные, которые точно не меняются при переносе

- Схема БД (`prisma/schema.prisma` + миграции) — про бронирование, сайт
  на неё не влияет.
- Telegram-бот и все API-роуты под `/api/**`.
- Бизнес-логика в `src/lib/**` (доступность, цены, защита от
  пересечений, уведомления).

Единственное, что меняется — где физически лежит разметка сайта
(`Main.dc.html` → `src/app/page.tsx`) и откуда открывается бронирование
(другой домен → `<Link>` внутри одного домена).
